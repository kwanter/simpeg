# Specification & Planning Preferences

- Writes feature specs to `spec/spec-feature-{name}.md`, prefixed with YAML front-matter (title, version, date created/updated, `status: Draft`, upstream PRD, target plan). Confidence: 0.65
- Structures specs with numbered requirement IDs (`REQ-`, `SEC-`, `CON-`) and a numbered acceptance-criteria list (`AC-`), where every criterion is checkable by an automated test or a deterministic command. Confidence: 0.7
- Includes a "Pre-Agreed Test Seams Matrix" mapping each requirement/criterion to its public seam, test level, and explicit mocking rules — naming which dependencies must be real versus which may be mocked (e.g. mocking a third-party PDF facade is allowed; mocking internal domain services is prohibited). Confidence: 0.65
- Includes explicit "Out of Scope" and "Open Questions & Assumptions" sections, and checks upstream artifacts (approved PRD, `CONTEXT.md`/`CONTEXT-MAP.md` glossary, `docs/adr/`) first — creating missing ones lazily on approval rather than inventing them upfront. Confidence: 0.6
- Pins structural constraints as greppable assertions (e.g. "controller must contain zero occurrences of X") alongside behavioral acceptance criteria. Confidence: 0.55
- Avoids making structural tests stricter than the documented contract: tests should assert required public methods are present, not require an exact method count when additional methods are permitted. Confidence: 0.8
- Writes implementation plans to `plan/plan-{name}.md` with YAML front-matter (goal, version, status, `upstream_spec`, `target_executor`, tags), and deliberately matches the `target_plan` path declared in the spec's front-matter over the template's default naming, to preserve cross-artifact traceability. Confidence: 0.6
- Plans execution as vertical tracer-bullet slices, explicitly rejecting horizontal/layer slicing; for a behavior-preserving refactor, redefines a slice as "one independently reviewable, releasable change where the entire existing suite stays green and exactly one structural goal is met." Confidence: 0.6
- Requires every acceptance criterion to be explicitly referenced by a covering ticket (later a test), iterating until 100% traceability with zero dangling references — including naming "oracle" criteria already pinned by existing tests so nothing is later flagged as missing coverage. Confidence: 0.65
- Gives each ticket exactly one atomic commit with explicit AC ownership, and ends each phase with VERIFY + APPROVAL checkpoints that stop and wait for user confirmation; includes a per-ticket rollback/recovery plan. Confidence: 0.55
- After remediating an artifact against an audit, marks the outcome on the audit report itself: prepends a remediation-status block (projected re-scored breakdown, per-finding closure) and leaves the original below it explicitly labelled "as audited before remediation / superseded" instead of rewriting the old numbers. Confidence: 0.55
- Audits traceability across the whole artifact chain and against the repository's recorded architectural memory (prior review reports, adr/, glossary), not just the immediate upstream document — and when the new spec reverses a previously recorded decision, cites that earlier document and states the reversal and its reasoning explicitly rather than silently contradicting it. Confidence: 0.6
- Keeps audits and remediations scoped to their own artifact: flags findings that belong to a downstream artifact (e.g. plan-side tickets) as out of scope for the spec pass and hands them off rather than editing the plan. Confidence: 0.5
- Revises plans in place with surgical edits rather than rewriting the file, preserving independently numbered tickets, their dependencies, and existing commit references; new tickets are appended (append-only numbering, e.g. adding Ticket-012 into an earlier phase) instead of renumbering existing ones. Confidence: 0.6
- Schedules safety-net pin tickets before the ticket that modifies the code they protect, on the principle that a pin added after the change is a description rather than a safety net; states the ordering constraint redundantly (dependency-graph edge plus assumption and rollback entries) so it cannot be missed. Confidence: 0.65
- Reports audit results as a numeric readiness score against an explicit threshold, broken down by weighted dimensions (completeness/clarity/alignment) with a critical-flaw veto that caps the score, and treats a below-threshold score as a gate that blocks progress until the findings are remediated. Confidence: 0.5
- Writes acceptance criteria that distinguish "inherited oracle" files (the characterization suite — must never be modified or deleted) from "refactor-owned" test files (created by this change, allowed to grow with new assertions); an AC conflating the two is flagged as a blocking ambiguity because a legitimate working-tree modification then reads as a gate failure. Confidence: 0.55
- Maintains an authoritative Execution Progress Ledger near the top of the plan (ticket → status → commit) that is synced to reality at each phase close, while explicitly stating that the per-ticket step checkboxes remain the approved plan of record and are not kept as live state. Confidence: 0.5
- Every amendment to a spec advances its front-matter `version` and appends a new dated remediation-history entry to the spec body (e.g. "Remediated a fourth time on … (version 1.2 → 1.3)") while leaving the prior entries intact — the spec is never edited silently, and the entry names the plan tasks/audit findings the amendment closes and why the earlier wording was deficient. Confidence: 0.5
- Keeps the spec's change-set inventory (new files / modified test infrastructure / new documentation) synchronized with the actual diff, and records any touched file that has no requirement behind it together with its justification (e.g. listing a `phpunit.xml` test-isolation change rather than leaving it orphaned) so an audit cannot re-flag it as untraceable. Confidence: 0.5
- When an optimization specifically aims to eliminate unnecessary work, wants the spec and acceptance criteria to pin that efficiency outcome directly (e.g. zero database queries), rather than requiring only equivalent functional output. Confidence: 0.7
- Avoids turning non-behavioral documentation-maintenance details into acceptance criteria when they neither change behavior nor define a public seam, since tests that lock comments or citations are brittle. Confidence: 0.75
