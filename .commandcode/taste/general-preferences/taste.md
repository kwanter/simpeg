# General Preferences
- Uses a TDD-first workflow driven by explicit governance/scaffolding artifacts — an `AGENTS.md` plus `.agents/` (rules, standards, skills) mirrored into `.claude/`, and generated `CONSTITUTION.md`/`CONSTRAINTS.md` calibrated to the project's stack. Confidence: 0.6
- Initiates development workflows through custom slash commands (e.g. `/tdd-init`, `/tdd-refactor-legacy`) rather than explaining setup step-by-step in prose. Confidence: 0.75
- For legacy refactoring, prefers characterization tests to capture existing behavior—including quirks—before production changes, rather than silently correcting behavior during the characterization phase. Confidence: 0.85
- Works in an Indonesian-language context (Bahasa Indonesia domain terms like `Pegawai`, `Cuti`, and Indonesian-language ticketing/communication). Confidence: 0.5
- Writes documentation/spec artifacts in English while holding the surrounding conversation in Bahasa Indonesia. Confidence: 0.6
- Prefers strictly behavior-preserving refactors: every observable behavior (routes, URLs, HTTP verbs, status codes, redirect targets, flash keys/messages, validation error keys/messages, rendered markup, persisted values) must stay byte-identical, and any behavior change is explicitly deferred and documented as out of scope rather than folded into the refactor. Confidence: 0.7
- Requires proof before deleting unreachable/dead code — demonstrates unreachability with an enumerated test (e.g. a policy-equivalence matrix) rather than a code-reading argument — while deliberately retaining defensive failure branches (e.g. an `abort(500)` guard) whose removal would turn a future error into a silent success. Confidence: 0.6
- Documents architectural decisions as ADRs, but only for decisions that are surprising, hard to reverse, and had no real alternative ("triple gate"); smaller service-extraction decisions follow established codebase patterns and are recorded as prose instead. Confidence: 0.55
- Marks unverified guesses explicitly (e.g. `[ASSUMPTION]` / `CLARIFICATION NEEDED`) for downstream interrogation instead of silently filling gaps. Confidence: 0.6
- When scope is ambiguous, asks a single focused question rather than a batch — presenting numbered options with an explicit recommendation — and expects a terse answer (e.g. "Opsi A"); performs deep codebase investigation before drafting artifacts. Confidence: 0.55
- When presented with options alongside a recommendation, tends to accept the recommended option without elaboration (answering with just a letter like "A"/"Opsi A"/"B", or a bare "lanjutkan rekomendasimu" telling the agent to carry out its own recommendation), delegating the substantive decision to the agent's rationale rather than debating alternatives. Confidence: 0.8
- Prefers intermediate workflow artifacts (e.g. clarification/audit reports) saved as versioned files inside the repository (e.g. under `docs/audit/`) rather than left only in the conversation, and explicitly asks for the report to be persisted in the repo before moving on to the next phase. Confidence: 0.6
- Never silently overwrites an existing artifact: when writing a new report into a directory that already holds one, picks a distinct filename so nothing is clobbered. Confidence: 0.5
- Follows the repository's existing conventions over framework-idiomatic defaults (e.g. places a new trait in `app/Traits` with an `XxxTrait` name because that is the repo's only precedent, explicitly rejecting the conventional `App\Http\Requests\Concerns`). Confidence: 0.6
- Recommends starting a fresh session for each workflow phase (spec → clarify → plan → execute) so personas and prior interrogation history do not mix. Confidence: 0.5
- Keeps strictly within the current phase's declared artifact scope and will not unilaterally change an upstream artifact's state (e.g. flipping a spec from `Draft` to `Approved`), instead flagging it and asking. Confidence: 0.55
- Runs dependency/security gates (`composer audit`, `npm audit`) and, more generally, reports any gate that cannot actually run (e.g. a Playwright/Chromium browser gate when `node_modules` is absent) as UNVERIFIED rather than passed, citing the project's constraints document for that rule and offering a structural argument as context while explicitly labelling it an argument rather than a test result. Confidence: 0.5
- Prefers driving toolchains through the project's own local binaries (`./vendor/bin/pint`, `./node_modules/.bin/playwright`) instead of `npx`/globally cached equivalents, checking first that the local install actually exists before treating a gate as runnable. Confidence: 0.5
- Issues terse, multi-part imperative instructions in Bahasa Indonesia that chain several workflow steps in a single message (e.g. "commit ticket 01,02,12 kemudian lanjut fase 2 dan selesaikan ASSUMPTION-007 via tdd-spec"), rather than one request per turn. Confidence: 0.6
- Is willing to invoke a later workflow skill/persona mid-session (e.g. `/tdd-spec` during an execution session) even when the agent has recommended opening a fresh session per phase, and explicitly overrides the session-lock/persona guard instead of splitting the work. Confidence: 0.65
- Reports weaknesses in its own verification honestly, distinguishing pre-existing working-tree state (e.g. a test file already modified in an earlier session) from this session's changes, and flags gates that produce false positives as needing refinement rather than quietly passing or hiding them. Confidence: 0.55
- After rewiring code, removes imports and now-stale comments that its own change orphaned — checking symbol usage with grep first and retaining anything still referenced — instead of leaving misleading leftovers. Confidence: 0.55
- When a verification gate reports a false positive caused by pre-existing uncommitted working-tree state, fixes it at the root (committing the pending work, noting it was not authored this session) and then re-runs the exact gate command to confirm it is empty, rather than suppressing, excluding, or ignoring the gate. Confidence: 0.5
- Sequences each phase as commits first, then a cross-artifact consistency audit (e.g. `/tdd-analyze` over spec + plan + the now-executed code treated as a fourth artifact) before starting the next phase; documentation that contradicts the repository's actual state (stale service inventory, claiming a glossary/ADR set does not exist) is reported as a blocking defect rather than a cosmetic nit. Confidence: 0.55
- Closes the entire outstanding remediation chain before resuming feature work: when an audit leaves findings open, instructs the agent to finish *all* of them (spec-side and plan-side, not just the ones already partially handled) rather than deferring them behind the next implementation ticket. Confidence: 0.5
- Prefers living documents (architecture maps, plan ledgers/caveats) to state the command that derives a quantity rather than quoting an exact count, after seeing values like file/test counts drift three times in one session; a bare number in prose is treated as a reliability defect. Confidence: 0.55
- When a delegated task rests on a false premise (e.g. a plan calls a file "already refactor-created" when it is actually inherited oracle), does not execute it as written and does not silently violate the governing rule: substitutes a compliant equivalent that satisfies the same requirement and reports the deviation with the exact rule/criterion IDs it would have breached. Confidence: 0.6
- Refuses work outside its current role boundary even when a plan instructs it — a Developer will not edit spec/acceptance-criteria text, routing that to the spec-authoring skill, on the grounds that redefining an acceptance criterion is a requirements decision rather than an implementation detail. Confidence: 0.55
- Verifies a reviewer's or plan's technical remedy against the actual dependency source (reading `vendor/...` and citing file:line) before adopting it, and reports the suggested fix as unworkable when it is — replacing it with a solution that actually addresses the concern rather than implementing advice that cannot work. Confidence: 0.55
- Does not assert consequence claims it has not empirically verified — before writing a comment stating that a change (e.g. dropping a field from `$fillable`) would break behaviour, runs the experiment to check; when the experiment disproves the claim, corrects the reasoning, keeps the code as-is for the *real* reason (here: removing it would move the source of truth for initial state from the service to the schema, a design decision rather than a tidy-up) and records the disproven experiment inline as a warning so the next reader does not re-run it — rather than leaving the false claim in place or silently deleting it. Confidence: 0.55
- Treats authoritative records as falsifiable rather than trustworthy: mechanically re-checks each claim against git reality (re-reading `git log` for every commit hash a ledger cites, confirming the subject matches and that listed deliverables are actually untracked) instead of assuming the record is accurate. Confidence: 0.5
- Drives a large, open-ended effort by re-issuing the same workflow slash command once per bounded batch (e.g. `/tdd-refactor-legacy` invoked ~10 times across a session, or resuming with just "lanjutkan sesi terakhir"), leaving the agent to choose the next slice/step itself rather than specifying it; answers a scope question with a maximal "semuanya"/everything. Confidence: 0.5
